## 타비도리 추가 지침

1. 먼저 읽는다: `docs/`의 관련 설계 문서와 `.claude/rules/`. 결정 기록과 다르게 쓰지 않는다. 문서끼리 충돌하면 스펙을 쓰기 전에 사용자에게 어느 쪽인지 묻는다.
2. 설계 문서의 용어(노드 이름, 화면 상태, 배지 이름 등)를 그대로 쓴다.
3. 스펙은 GitHub 이슈 본문으로 출력한다(dev-flow ② 형식과 함께 쓸 수 있다). 이슈 등록은 사람이 한다.
4. 한국어로 쓴다. 확인 안 된 사실은 "미확인"으로 표시한다.

## 원본 지침 (번역·요약)

이 스킬은 지금까지의 대화와 코드 이해를 스펙으로 만든다. 사용자를 다시 인터뷰하지 않는다 — 이미 아는 것을 정리만 한다. (빈틈이 많으면 먼저 `grill`로 다듬자고 제안한다.)

### 과정

1. 코드가 있으면 현재 상태를 살펴본다. 프로젝트 용어를 쓰고, 그 영역의 기존 결정을 지킨다.
2. 이 기능을 시험할 이음매(seam)를 정한다. 기존 이음매를 우선 쓰고, 가능한 한 높은 지점 하나로. 사용자에게 이 이음매가 맞는지 확인한다.
3. 아래 틀로 스펙을 쓴다.

### 스펙 틀

```
## 문제        사용자 입장에서 겪는 문제
## 해결        사용자 입장에서 본 해결
## 사용자 이야기   번호 목록. "<누구>로서, <무엇>을 원한다, <왜>이기 때문에"
## 구현 결정    만들거나 고칠 모듈, 인터페이스, 구조 결정, DB 변경, API 약속.
               파일 경로·코드 조각은 넣지 않는다(금방 낡음).
               예외: 상태 기계·스키마·타입 모양처럼 글보다 정확한 것은 필요한 부분만.
## 시험 결정    좋은 시험의 기준(내부 구현이 아니라 바깥 동작만), 시험할 모듈
## 범위 밖      이 스펙에서 하지 않는 것
## 그 밖의 메모
```
