# 코드 워크스루

**사용자가 설명할 수 없는 코드를 커밋하지 않는다.** 이 팀은 코드 대부분을 AI로 쓴다. 그래서 이 단계가 "내가 만든 코드"로 만드는 유일한 단계다.

## 5단계 — 사용자가 보는 것에서 시작해 코드로 들어간다

### ① 무엇이 문제였나 / 무엇을 만들었나
화면에서 보이는 것으로 쓴다. 내부 용어로 시작하지 않는다.

### ② 어디를 고쳤나
파일과 변경 전/후. 짧게.

### ③ 이 코드가 뭔 뜻인가 ← 빠뜨리기 쉬운 단계
**기본 문법이 아닌 것은 전부 설명한다.** 특히 프론트 문법은 팀원이 낯설다.

```
useEffect(() => {...}, [spots])   spots가 바뀔 때마다 안의 코드를 다시 실행
?.                                 앞이 null·undefined면 멈추고 undefined
Depends(get_db)                    FastAPI가 요청마다 DB 세션을 만들어 넣어 준다
model_validate(data)               Pydantic이 data를 검사해서 모델로 바꾼다. 틀리면 오류
```

### ④ 어떤 흐름으로 도나
실행 순서. ASCII 그림이 글보다 잘 읽힌다.

```
사용자가 [검증하기] 클릭
  ├─ frontend: POST /api/verify
  ├─ backend router → verify.service
  │     └─ 백트래킹으로 순서 시험 → 스트림으로 한 단계씩 전송
  └─ frontend stream/ → 지도에 경로 그리기
```

### ⑤ 왜 그 방법인가
**버린 대안을 같이 적는다.**

## 형식

표와 코드 블록 위주. 실측값이 있으면 넣는다("빨라졌다"가 아니라 "1.9초 → 0.4초").

## 하지 않을 것

- 변경 파일을 나열하고 끝내지 않는다(그건 `git diff --stat`).
- "~하도록 수정했습니다"로 끝내지 않는다. **왜 그게 동작하는지**를 설명한다.
- 모르는 것을 아는 척하지 않는다. 라이브러리 동작이 불확실하면 소스·문서를 읽고, 읽었다고 말한다.
